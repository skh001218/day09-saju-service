# 008: 내 오행과 성향에 잘 맞는 사람 유형 안내

## 목적과 확정한 범위

사용자가 자신의 사주 해석을 읽을 때 함께 지내기 편할 수 있는 사람의 **오행·성향 유형 2~3가지**와 그 이유를 쉬운 말로 확인하게 합니다. 사용자는 두 사람의 생년월일을 비교하는 궁합 대신 **내 결과를 바탕으로 한 유형 안내**, 고정 규칙 대신 **Gemini의 설명 생성**, 기존 **자세히 해석하기** 결과에 포함, **계정 기록에 저장**하는 방식을 선택했습니다.

이 안내는 전통적 오행 이미지를 활용한 대화 소재입니다. 실제 사람의 성격, 관계의 성공 여부, 우열을 판정하지 않습니다. 상대방의 오행 하나만으로 궁합이 결정된다고 표현하지 않습니다.

## 사용자 흐름

1. 사용자는 기존 방식으로 양력 생년월일과 출생시간을 입력해 사주를 계산합니다. 네 기둥, 일간, 기본 성향, 오행 개수는 로그인 없이 그대로 봅니다.
2. 로그인한 사용자가 **자세히 해석하기**를 누르면 기존 성향·강점·주의점 및 로스트아크 직업 추천과 함께 **잘 맞는 사람 유형** 영역을 생성합니다. 별도 버튼이나 자동 Gemini 호출은 추가하지 않습니다.
3. 유형은 **2개 또는 3개**입니다. 각각 `오행 이름`, `쉽게 읽는 성향`, `함께 지낼 때 기대할 수 있는 점과 그 이유`를 보여줍니다. 같은 오행을 중복 추천하거나 점수·순위를 매기지 않습니다. 이유는 내 계산 결과의 특성과 추천 유형의 특성을 연결합니다.
4. 결과 화면에서 유형마다 오행 이름과 문장을 함께 표시합니다. 색만으로 구분하지 않고 작은 화면에서도 읽을 수 있어야 합니다. 안내 바로 옆에 실제 관계는 가치관·행동·소통에 따라 달라진다는 취지의 문구를 표시합니다.
5. 새 결과는 기존 해석과 같은 계정 기록 한 건에 저장합니다. 목록에서 다시 열거나 새로고침·재로그인 후 다시 열면 저장 당시의 유형과 이유를 그대로 보여주고 Gemini를 재호출하지 않습니다.
6. 기능 도입 전 계정 기록 및 기존 브라우저 `localStorage` 기록에는 유형을 소급 생성하지 않습니다. 해석은 계속 열리고 “이전 기록에는 사람 유형 안내가 없습니다”라고 표시합니다. 새 입력·다른 기록 열기·로그아웃 시 이전 화면의 유형이 다른 사주의 결과처럼 남지 않도록 합니다.

## 생성 기준과 데이터 형식

- 서버가 기존 `lib/saju`로 사주를 계산하고, 계산된 네 기둥·일간·대표 오행 개수와 기존 기본 성향 해석 기준을 Gemini에 전달합니다. 생년월일·출생시간, 계정 식별자, 인증 토큰은 Gemini에 보내지 않습니다. Gemini에게 사주 계산을 맡기지 않습니다.
- Gemini는 기존 해석 요청 **한 번**에서 기존 해석·직업 추천과 함께 `compatible_types` 배열을 생성합니다. 각 항목은 `element`(`목`, `화`, `토`, `금`, `수` 중 하나), `tendency`(쉬운 성향 한 문장), `reason`(내 결과와 연결한 이유 1~2문장)으로 구성합니다. 배열 길이는 2 또는 3이고 오행은 서로 달라야 합니다.
- 프롬프트는 일간 오행과 오행 개수를 참고하되, 006 Spec의 단순 집계를 강약·결핍·용신 판정으로 확장하지 않도록 명시합니다. 상생·상극 같은 단일 관계만으로 사람의 적합성을 확정하지 않습니다. 성별, 나이, 출생 연도, 장애 등 인구학적 특성을 추천 기준으로 쓰지 않습니다.
- 서버는 배열 길이, 허용 오행, 중복 여부, 필수 문자열의 공백·길이(각 10~300자), 응답 구조를 검사합니다. 문구가 실제 성격이나 관계를 확정하거나 상대의 출생 정보가 있는 듯 꾸며낸 결과는 성공으로 취급하지 않도록 프롬프트와 검증 기준을 둡니다. 자동으로 판별하기 어려운 표현은 실제 화면 검토 항목으로 남깁니다.
- 추천은 **유형**을 설명합니다. 특정 실존 인물, 다른 사용자 계정, 연락처, 프로필을 찾거나 연결하지 않습니다. 다른 사람의 생년월일을 입력받지 않습니다.

## 저장과 이전 기록

- 기존 `public.saju_interpretations`에 유형 배열을 보관할 `compatible_types` JSONB 열을 추가하는 새 migration을 작성합니다. 새 결과는 검증된 2~3개 항목을 필수로 저장하고, 과거 행은 `NULL`을 허용합니다. 저장·조회 API와 클라이언트 형식 검사는 새 기록과 과거 기록을 모두 처리합니다.
- 서버가 생성·검증한 값만 저장합니다. 브라우저가 보낸 유형이나 사용자 ID를 저장 근거로 신뢰하지 않습니다. 계정별 세션 검증과 RLS는 004 Spec을 따릅니다. 기존 브라우저 기록 구조를 변경하거나 유형을 `localStorage`에 새로 저장하지 않습니다.
- 동일 `request_id`의 재요청은 저장된 해석과 유형을 그대로 반환하고 Gemini를 재호출하거나 기록을 중복 생성하지 않습니다. 동시 요청의 중복 저장 처리에서도 유형이 누락되지 않아야 합니다. 기록 삭제 시 유형도 함께 삭제됩니다.

## 실패와 재시도

- 잘못된 입력·비로그인·만료 세션은 기존 흐름대로 Gemini 호출 전에 거부합니다.
- Gemini 호출 실패, 형식 오류, 유형 개수 부족·초과, 허용되지 않는 오행, 중복 오행, 빈 문구가 있으면 새 해석을 성공 처리하거나 저장하지 않습니다. 계산된 사주와 기본 성향은 유지하고 오류와 재시도 방법을 보여줍니다. 가짜 유형이나 임의의 기본값으로 대체하지 않습니다.
- Gemini 결과는 유효하지만 계정 저장만 실패하면 기존 정책에 따라 현재 화면에 결과를 보여주되 **저장되지 않았음**을 명확히 알립니다. 기록 목록에 성공한 것처럼 추가하지 않습니다.
- 과거 기록의 유형 없음은 오류가 아닙니다. 기록 자체의 성향·직업 추천 등 기존 내용은 그대로 표시합니다.

## 이번 범위에서 제외

- 두 사람의 실제 궁합 계산·비교, 상대의 출생 정보 입력, 사용자 검색·매칭·연락 기능
- 연애 성사율, 관계 점수·순위, 운명적 상대 단정, 결혼 시기·미래 예측
- 오행 강약·용신·희신의 새 계산, 기존 오행 집계 방식 변경
- 비로그인 Gemini 생성, 과거 기록의 자동 재해석·일괄 갱신

## 완료 조건과 검증 사례

1. 로그인 사용자가 유효한 사주에서 **자세히 해석하기**를 누르면 기존 해석·직업 추천과 서로 다른 오행 유형 2~3개, 성향·이유, 비단정 안내가 보입니다. 별도 요청이나 버튼은 없습니다.
2. 새 결과가 기존 계정 기록 한 건에 저장되고 재열기·새로고침·재로그인 시 동일하게 보입니다. 같은 `request_id` 재요청은 결과와 기록을 중복 생성하지 않습니다.
3. 기능 도입 전 계정 기록과 브라우저 기록은 계속 열리고 유형 없음 안내가 보이며 데이터가 변하지 않습니다. 사용자 A의 유형은 사용자 B에게 보이지 않습니다.
4. 유효하지 않은 입력·비로그인에는 Gemini 호출이 없고, 잘못된 Gemini 응답에는 새 해석/유형 저장 없이 오류·재시도가 보입니다. 저장만 실패한 경우에는 화면 결과와 미저장 안내가 보입니다.
5. 새 입력·기록 전환·로그아웃 뒤 이전 유형이 남지 않습니다. 모바일 화면에서 2개와 3개 항목 모두 읽을 수 있습니다.
6. 관련 자동 테스트, 타입 검사, 빌드와 실제 화면에서 정상 생성·저장·재열기·오류·재시도 및 기존 계산·기록 흐름을 확인한 뒤에만 `docs/status.md`를 완료로 표시합니다. 구현하지 않은 현재 단계에서는 검증 성공을 기록하지 않습니다.

## 현재 상태

기능 코드, 화면, 계정 기록 저장·조회와 DB migration을 작성했습니다. 실제 로그인·Gemini 생성·계정 기록 재열기 화면 검증이 남아 있어 완료 전입니다.
