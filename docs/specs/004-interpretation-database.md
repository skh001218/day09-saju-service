# 004: 로그인 사용자의 사주 해석 결과 데이터베이스 저장

## 목적과 선행 조건

로그인한 사용자가 Gemini 해석 결과를 계정에 연결해 저장하고, 다른 기기에서도 자신의 결과를 다시 열거나 삭제할 수 있게 합니다. 로그인은 `003-google-login.md`의 Supabase Auth Google 로그인을 선행 조건으로 가정합니다.

## 사용자가 확정한 정책

- 비로그인 사용자는 사주 계산과 기본 성향 한 문장까지 볼 수 있습니다. Gemini의 **자세한 해석과 새 결과 저장은 로그인한 사용자만** 사용할 수 있습니다.
- 로그인 후 **새로 생성한 해석**은 계정의 Supabase Postgres에 저장합니다. 새 해석은 `localStorage`에 추가하지 않습니다.
- 기존 `localStorage` 기록은 삭제·변경·자동 업로드하지 않고, 해당 브라우저에 그대로 둡니다. 다른 계정의 소유자임을 확인할 수 없는 기록이므로 자동 업로드하지 않습니다.
- 여러 기록을 허용하고, 동일한 생년월일·출생시간으로 사용자가 명시적으로 새 해석을 받으면 별도 기록으로 남깁니다. 단, 같은 해석 요청의 네트워크 재전송은 중복 저장하지 않습니다.

## 데이터 모델

테이블 이름: `public.saju_interpretations`. 데이터베이스 변경은 구현 단계의 재현 가능한 migration으로 관리합니다.

| 열 | 형식 / 제약 | 의미 |
|---|---|---|
| `id` | `uuid PRIMARY KEY`, 기본값 `gen_random_uuid()` | 기록 식별자 |
| `user_id` | `uuid NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE` | 로그인한 소유자. 요청 본문이 아닌 검증된 세션에서 결정 |
| `request_id` | `uuid NOT NULL`, `(user_id, request_id)` 고유 제약 | 같은 해석 요청을 재전송해도 한 번만 저장하기 위한 값 |
| `birth_date` | `date NOT NULL` | 사용자가 입력한 양력 생년월일 |
| `birth_time` | `time without time zone NOT NULL` | 사용자가 입력한 출생 시각. 시간대 변환 없이 입력한 시각 그대로 보관 |
| `chart` | `jsonb NOT NULL` | 서버가 다시 계산한 네 기둥·일간·오행 등 `SajuChart` |
| `personality` / `strengths` / `cautions` | 각각 `text NOT NULL` | 서버가 형식 검사를 마친 Gemini 해석 세 부분 |
| `model` | `text NOT NULL` | 해석 생성에 사용한 모델 이름 |
| `created_at` | `timestamptz NOT NULL DEFAULT now()` | 서버의 저장 시각 |

`user_id`와 `created_at`을 선두로 하는 최신순 목록 인덱스, `user_id` 필터 인덱스를 둡니다. `(user_id, request_id)` 고유 제약의 인덱스를 중복해서 만들지 않습니다. `chart`의 구조와 세 해석 문자열은 서버에서 저장 전에 검증합니다. 입력 허용 범위는 기존 계산 규칙인 1990-01-01 이후 양력 날짜와 유효한 출생시간을 그대로 따릅니다. 가능한 경우 데이터베이스에도 필수 값·길이 등의 기본 제약을 둡니다. API 키나 Google 인증 토큰은 이 테이블에 저장하지 않습니다.

## 접근 제어와 서버 신뢰 경계

- 테이블에 Row Level Security(RLS, 데이터베이스가 각 행에 적용하는 접근 규칙)를 켜고, `anon`의 읽기·쓰기 권한은 부여하지 않습니다. `authenticated`에는 이 기능에 필요한 `SELECT`, `INSERT`, `DELETE`만 허용하고 `UPDATE`는 허용하지 않습니다.
- `SELECT`와 `DELETE`의 `USING`, `INSERT`의 `WITH CHECK`에서 모두 `user_id = (select auth.uid())`를 요구합니다. 다른 사용자의 ID를 지정해 읽거나, 자기 소유로 보이는 행을 타인 소유로 생성할 수 없어야 합니다. `user_id`는 `NOT NULL`이므로 미인증 `auth.uid()`의 `NULL`과 일치하지 않습니다.
- API는 요청마다 Supabase Auth 세션을 서버에서 검증하고, 검증된 사용자 ID를 기준으로 사용자 범위를 제한합니다. 브라우저가 보낸 `user_id`, 사주 계산값, 모델명, 생성 시각은 신뢰하지 않습니다. 서버는 입력 날짜·시간으로 `lib/saju`의 사주를 다시 계산하고, Gemini 응답을 기존 `parseInterpretation` 기준으로 검사합니다.
- 데이터베이스 요청은 그 사용자의 인증 정보가 적용되는 클라이언트로 수행해 RLS를 반드시 통과시킵니다. RLS를 우회하는 `service_role` 비밀키를 일반 저장·조회·삭제 요청에 사용하지 않습니다. Supabase 공개키는 접근 통제 수단이 아니며, 실제 보호는 인증 검증과 RLS가 담당합니다.
- 결과를 돌려주는 API에는 `Cache-Control: no-store`를 적용합니다. 비밀키·세션 토큰·생년월일·해석 원문을 오류 로그에 남기지 않습니다. Gemini에는 기존과 같이 계산된 사주 정보만 전달하고 원래 생년월일·출생시간은 보내지 않습니다.
- 데이터베이스 migration과 RLS 정책은 서로 같은 배포 단위로 적용합니다. 공식 가이드에 따라 권한(grant)과 RLS 정책을 둘 다 확인합니다. [Supabase RLS 문서](https://supabase.com/docs/guides/database/postgres/row-level-security), [Supabase 서버 인증 문서](https://supabase.com/docs/guides/auth/server-side)

## 화면과 API 흐름

1. 비로그인 상태에서는 사주 계산·기본 성향과 **기존 브라우저 기록 열람**을 유지합니다. 새 **자세히 해석하기**에는 로그인 필요 안내를 보여줍니다. 로그인 상태에서는 계정 저장임을 명확히 표시하고 해당 계정의 목록을 불러옵니다. 과거 브라우저 기록은 별도 목록으로 출처를 구분해 표시합니다.
2. 사용자가 **자세히 해석하기**를 누르면 클라이언트는 해당 요청의 `request_id`를 생성하고 생년월일·출생시간을 `POST /api/interpret`에 보냅니다. 서버가 입력 검증·사주 재계산·Gemini 호출·응답 검증을 수행합니다.
3. 서버는 Gemini 호출 **전** 유효한 로그인 세션을 확인하고, 같은 사용자·`request_id`의 저장된 결과가 있으면 Gemini를 다시 호출하지 않고 그 결과를 반환합니다. 비로그인·만료 세션의 `POST /api/interpret`는 인증 오류로 거부하고 Gemini를 호출하거나 새 기록을 저장하지 않습니다. 새 요청이면 생성한 해석을 `saju_interpretations`에 삽입한 뒤 저장된 기록과 해석을 반환합니다. 저장 실패를 브라우저 저장으로 조용히 전환하지 않습니다.
4. 로그인 사용자의 결과 목록은 `GET /api/results`에서 자신의 기록만 최신순으로 조회합니다. 첫 화면은 최근 20건을 표시하고, 더 오래된 기록은 페이지 단위로 추가 조회할 수 있게 합니다. 목록 항목에서 기록을 열면 당시 입력, 서버 계산 결과, 해석 세 부분을 함께 표시합니다.
5. 개별 삭제는 확인 후 `DELETE /api/results/{id}`로 처리합니다. 서버는 검증된 사용자의 본인 기록만 삭제하며, 성공한 뒤 목록에서 해당 항목을 제거합니다. 다른 사용자 소유 ID나 존재하지 않는 ID는 내용 또는 소유 여부를 노출하지 않는 동일한 비공개 응답으로 처리합니다.
6. 로그아웃하면 화면에 남은 계정 결과·목록을 지우고, 이후 계정 API를 호출하지 않습니다. 브라우저 기록은 원래대로 남되 계정 기록으로 표시하지 않습니다.

## 기존 브라우저 기록 처리

현재 `lib/saju/history.ts`의 `saju-results-v1` 기록은 유지하며 삭제·변경·자동 업로드하지 않습니다. 같은 브라우저를 여러 사람이 사용할 수 있고 기존 기록에는 계정 소유자 정보가 없으므로 로그인 직후 계정에 귀속시키지 않습니다. 과거 기록은 로그인 전후 모두 “이 브라우저에만 저장됨”으로 구분해 볼 수 있게 하고, 계정 목록과 섞어 동기화된 것처럼 표시하지 않습니다. 로그아웃 시 계정 결과는 지우되 과거 브라우저 기록의 열람은 유지합니다. `localStorage`는 비밀 보관소가 아니므로 공용 브라우저에서 다른 사람이 볼 수 있다는 경고를 유지합니다. 과거 기록을 선택해 계정으로 가져오는 수동 이전 기능은 이번 범위에서 제외합니다. 다른 기기에서는 계정 기록만 보이고 기존 브라우저 기록은 보이지 않는다고 안내합니다.

## 실패, 중복, 데이터 검증

- 해석 생성 자체가 실패하면 기존처럼 계산 결과를 유지하고 오류·재시도를 보여주며 데이터베이스에 행을 쓰지 않습니다.
- Gemini 해석은 성공했으나 데이터베이스 저장에 실패하면 해석은 현재 화면에서 읽을 수 있게 하되, **계정에 저장되지 않았음**을 명확히 알립니다. 목록에 저장 성공처럼 표시하지 않습니다. 재시도는 Gemini를 다시 호출할 수 있어 추가 사용량이 발생할 수 있음을 구현 단계에서 고려합니다.
- 네트워크 응답이 끊겼지만 삽입은 성공했을 수 있습니다. 동일 요청을 재시도할 때 `request_id`로 기존 행을 먼저 확인하고 있으면 중복 생성 없이 기존 결과를 돌려줍니다. 새 해석을 명시적으로 요청할 때만 새 `request_id`를 사용합니다. 고유 제약 충돌도 같은 요청의 기존 결과 반환으로 처리합니다.
- 로그인 세션 만료 시 목록·삭제·저장은 실패로 안내하고 재로그인 경로를 제공합니다. 권한 실패를 “저장된 결과가 없음”으로 숨기지 않습니다.
- 잘못된 입력, 조작된 `user_id`·`chart`·해석 본문, 유효하지 않은 UUID, 비정상적으로 큰 요청, 손상된 저장 행은 거부하거나 안전하게 건너뛰고, 화면을 멈추지 않게 합니다. 저장 행의 표시 직전에도 필요한 형식 검사를 수행합니다.
- 목록 조회 실패·삭제 실패는 기존 화면 데이터를 임의로 지우지 않고 다시 시도할 수 있게 합니다. 삭제 성공 시 현재 열어 둔 항목이 삭제 대상이면 상세 표시도 지웁니다.

## 이번 범위에서 제외

- 브라우저 기록의 자동·수동 계정 이전, 여러 계정 사이 기록 공유
- 해석 수정, 대량 삭제, 계정 탈퇴 화면, 다운로드·백업, 결제
- Gemini 프롬프트 변경, 사주 계산 범위 확장, 결과를 이용한 개인화 추천
- 서비스 배포, 기존 브라우저 기록 자동 이전

## 완료 조건과 검증 사례

1. 로그인 사용자 A가 새 해석 두 건을 저장하면 새로고침 및 다른 기기에서 자신의 두 건을 조회·재열기할 수 있습니다. 사용자 B나 비로그인 요청은 A의 행을 `SELECT`·`DELETE`할 수 없고, A의 `user_id`로 `INSERT`할 수 없습니다.
2. A가 기록 하나를 삭제하면 그 항목만 사라지고 다른 항목은 남습니다. B의 ID를 지정한 삭제는 B의 데이터를 변경하지 않습니다.
3. 비로그인 사용자는 계산·기본 성향·기존 브라우저 기록을 볼 수 있지만 Gemini 해석 요청과 새 기록 저장은 사용할 수 없습니다. 로그인 후 새 결과는 DB에만 저장되고, 기존 브라우저 기록은 자동으로 DB에 추가되지 않으며 별도 목록에 남습니다.
4. 동일 `request_id`의 재전송은 한 행만 만들고 같은 결과를 반환합니다. 새 해석 요청은 새 행을 만들 수 있습니다.
5. Gemini 실패, 저장 실패, 인증 만료, 목록 실패, 삭제 실패에서 잘못된 성공 표시·가짜 결과·타인 데이터 노출이 없고 재시도 방법이 보입니다.
6. RLS는 인증 사용자 A/B와 미인증 역할 각각에 대해 허용·거부 테스트를 작성합니다. 관련 자동 테스트, 타입 검사, 실제 브라우저의 로그인→해석→저장→새로고침→재열기→삭제 및 로그아웃 흐름을 확인한 뒤에만 `docs/status.md`를 완료로 바꿉니다.

## 구현·검증 현황 (2026-09-23)

- 사용자별 RLS와 테이블 정의의 재현 가능한 SQL migration, 로그인 필수 해석·저장 API, 계정 기록 목록·삭제 API, 화면의 계정/이전 브라우저 기록 구분을 구현했습니다.
- 자동 테스트 47개와 타입 검사, 배포용 빌드가 통과했습니다. 실제 브라우저에서 비로그인 해석 차단과 이전 기록 보존을 확인했고, HTTP 요청에서 비로그인 해석·계정 목록이 모두 401로 거절됨을 확인했습니다.
- 처음에는 Supabase MCP 쓰기 도구의 승인 정책이 `never`여서 적용이 차단됐습니다. 이후 참가자가 승인한 뒤 Supabase SQL Editor에서 동일한 SQL을 실행했고 `Success. No rows returned`를 확인했습니다. Table Editor에 `public.saju_interpretations`가 나타났고 Policies 화면에서 RLS 활성화 및 본인 기록용 SELECT·INSERT·DELETE 정책 세 개를 확인했습니다. SQL Editor를 통한 수동 적용이므로 Supabase migration 이력 등록은 별도로 확인하지 않았습니다.
- 실제 Google 계정으로 저장·조회·삭제하는 흐름과 A/B 계정별 RLS 거부 테스트는 아직 수행하지 못했습니다. 완료 상태로 표시하지 않습니다.
