# 003: Google 로그인

## 목적과 현재 상태

Google 계정으로 로그인한 사람을 식별해, 후속 `004` Spec의 데이터베이스 저장 결과를 본인만 다시 볼 수 있게 합니다. 구현 전 앱은 로그인 없이 사주를 계산하고 Gemini 해석을 요청하며, 결과를 브라우저 `localStorage`에 보관했습니다. 기존 기록은 보존합니다.

## 확정된 사용자 결정과 설계 전제

- **설계 전제:** 이미 연결한 Supabase 프로젝트의 **Supabase Auth + Google OAuth**를 사용합니다. OAuth는 Google 비밀번호를 앱에 전달하지 않고 Google의 동의를 거쳐 로그인하는 방식입니다. 이 전제는 이 Spec 작성용이며 서비스 정책 확정은 아닙니다.
- **사용자 결정:** 비로그인 상태에서도 사주 계산과 기본 성향 한 문장, 기존 브라우저 기록 열람은 가능합니다. **Gemini 자세한 해석 요청과 새 결과 저장은 로그인해야 가능합니다.** 화면 버튼뿐 아니라 `/api/interpret` 서버에서도 로그인 여부를 검증합니다.
- **사용자 결정:** 기존 `localStorage` 기록은 그대로 둡니다. 로그인해도 자동으로 계정에 업로드하거나 삭제하지 않습니다. 로그인 후 새로 생성한 해석 결과만 `004`의 데이터베이스 저장 대상으로 삼습니다. 공용 브라우저에 남아 있는 타인의 기록을 잘못 계정에 귀속시키지 않기 위해서입니다.

## 사용자 화면 흐름

1. 첫 화면은 현재의 사주 입력·계산과 기본 성향 표시를 그대로 보여줍니다. 로그인하지 않은 상태에는 **Google로 로그인** 버튼과 “자세한 해석과 새 결과 저장은 로그인 후 가능”이라는 안내를 보여줍니다. 기존 브라우저 기록은 로그인 전에도 볼 수 있습니다. 비로그인 상태에서 자세한 해석을 누르면 로그인 안내가 나오며 Gemini 요청은 보내지 않습니다.
2. 버튼을 누르면 Google 인증 화면으로 이동합니다. 앱은 로그인 진행 중 중복 클릭을 막고, 필요한 경우 현재 페이지로 돌아올 경로만 전달합니다.
3. 동의가 끝나면 앱의 `/auth/callback`으로 돌아옵니다. 성공하면 첫 화면으로 이동해 로그인 상태와 **로그아웃** 버튼을 표시합니다. 이메일을 표시한다면 계정 확인 목적의 최소 표시만 하고, 저장된 사주와 같은 화면에 노출되는 개인정보임을 고려합니다.
4. 사용자가 취소하거나 인증이 실패하면 원래 화면으로 돌아와 쉬운 오류 안내와 재시도 버튼을 보여줍니다. 기존 입력, 계산 결과, 브라우저 기록은 임의로 삭제하지 않습니다.
5. 로그아웃하면 **현재 브라우저의 로그인 세션만** 끝내고 화면을 비로그인 상태로 전환합니다. 다른 기기의 로그인까지 끊지 않습니다. 로그아웃 자체는 데이터베이스 결과를 삭제하지 않으며, 이미 이 브라우저에 남아 있는 `localStorage` 기록도 자동 삭제하지 않습니다. 따라서 공용 기기에서는 브라우저 기록이 계속 보일 수 있음을 명확히 안내합니다.
6. 페이지를 새로고침해도 유효한 세션은 유지됩니다. 세션이 만료되거나 취소되면 비로그인 상태로 전환하며, 계정 전용 데이터는 보이지 않게 합니다.

## 인증 구조

- Next.js 16 App Router에서 `@supabase/ssr`의 브라우저 클라이언트와 서버 클라이언트를 분리합니다. 세션은 클라이언트와 서버가 공유하는 쿠키 기반으로 관리합니다. 앱의 기존 `localStorage` 사주 기록과 인증 세션은 별개입니다.
- 브라우저에서 `signInWithOAuth({ provider: "google", options: { redirectTo: "<허용된 앱 주소>/auth/callback" } })`로 시작합니다. 서버 렌더링에 맞는 PKCE 흐름을 사용합니다. PKCE는 로그인 도중 가로챈 일회용 코드를 다른 곳에서 쓰기 어렵게 하는 보호 절차입니다.
- Supabase가 Google 응답을 받은 뒤 앱의 `/auth/callback`으로 돌려보내면, 콜백 Route Handler에서 `code`를 `exchangeCodeForSession`으로 교환하고 쿠키에 세션을 반영합니다. `code`가 없거나 교환에 실패하면 인증 실패 화면으로 보냅니다. `next` 같은 복귀 경로를 허용한다면 내부 상대 경로만 허용해 외부 사이트로의 임의 이동을 막습니다.
- Next.js 16의 `proxy.ts`에서 Supabase 세션 갱신 흐름을 연결합니다. 서버에서 보호가 필요한 요청은 쿠키 내용만 믿지 않고 `auth.getClaims()`로 서명이 검증된 사용자 식별자를 확인합니다. 최신 계정 상태가 꼭 필요한 곳은 `getUser()`를 사용합니다. `getSession()`의 사용자 객체만으로 데이터 접근을 허가하지 않습니다.
- 로그인 상태의 화면 표시는 클라이언트 상태 변화 및 서버 확인 결과와 동기화합니다. 버튼을 숨기는 것만으로 보호하지 않고, `/api/interpret`와 `004`의 서버 API·데이터베이스 접근에서 별도로 권한을 검사합니다. 비로그인 해석 요청은 Gemini를 호출하기 전에 인증 오류로 거절합니다.
- 인증·개인화된 응답과 세션 갱신 응답은 다른 사용자에게 캐시되지 않도록 설정합니다. 쿠키 갱신 시 Supabase의 캐시 관련 응답 헤더를 보존합니다.

## 외부 서비스 설정 및 비밀값

- Google Cloud에서 웹용 OAuth Client ID/Secret과 동의 화면을 설정하고, Supabase 대시보드의 Google 공급자 설정에 등록합니다. Google의 **승인된 리디렉션 URI**에는 Supabase 프로젝트의 Auth callback 주소를 등록합니다. 앱의 `/auth/callback`은 Google 쪽이 아니라 Supabase의 **Redirect URLs 허용 목록**에 등록합니다. 개발용 `http://localhost:3000/auth/callback`과 실제 배포 주소를 각각 확인합니다.
- 필요한 최소 범위의 Google 프로필/이메일 권한만 요청합니다. Google Drive, Calendar 같은 추가 권한이나 Google API 호출은 이 범위 밖입니다.
- 앱에는 Supabase URL과 브라우저용 publishable key만 공개 설정값으로 둡니다. Google Client Secret, Supabase service-role/secret key, 사용자 access/refresh token은 클라이언트 코드·Git·로그·사주 기록에 저장하거나 출력하지 않습니다. 공개 가능한 publishable key도 데이터베이스 권한을 대신하지 않습니다.
- 로그인은 Google/Supabase와 사용자 정보를 주고받습니다. 이를 로그인 화면/개인정보 안내에 설명합니다. 사주 입력·해석 데이터는 로그인만으로 Google에 전달되지 않으며, `004`의 명시된 저장 흐름에서만 Supabase 데이터베이스로 전송합니다.

## `004` 데이터베이스 Spec과의 접점

- 데이터베이스 기록의 소유자는 화면에서 보낸 이메일이나 user ID가 아니라, **서버에서 검증된 Supabase Auth `user.id`**로 결정합니다. 이메일은 변경될 수 있으므로 소유권 키로 쓰지 않습니다.
- `004`는 로그인된 사용자에게만 DB 저장·조회·삭제를 허용하고, Row Level Security(RLS: 행마다 소유자 접근을 제한하는 데이터베이스 규칙)를 적용해야 합니다. 비로그인 또는 만료된 세션의 DB 요청은 명확한 인증 오류로 처리합니다.
- `003`의 로그인 완료만으로 브라우저 기록을 DB로 복사하지 않습니다. 기존 브라우저 기록은 그대로 보존하며, 로그인 이후 **새로 생성된 해석 결과만** `004`의 DB 저장 대상으로 합니다. 두 저장소를 구분해 보여야 합니다. 로그아웃/계정 전환 때 이전 계정의 DB 결과가 화면에 남지 않도록 클라이언트 상태를 지웁니다.
- 현재 `/api/interpret`는 로그인 없이 서버에서 사주를 다시 계산한 뒤 Gemini를 호출합니다. 새 정책에 맞춰 로그인 검증을 추가해야 하며, 미인증 요청은 Gemini를 호출하지 않고 거절합니다. DB 저장을 별도 요청으로 할지, 해석 성공 응답 뒤 연계할지는 `004`에서 정하되, 로그인 정보나 브라우저가 보낸 소유자 ID를 그대로 신뢰하지 않습니다.

## 실패·보안·개인정보 조건

- Google 인증 취소, 공급자 미설정, 허용되지 않은 Redirect URL, 콜백 코드 누락/교환 실패, 네트워크 오류에 각각 복구 가능한 안내를 보여줍니다. 내부 토큰·코드·Client Secret이나 상세 서버 오류는 화면에 노출하지 않습니다.
- 세션이 만료되면 자세한 해석 요청과 계정 전용 목록·저장·삭제를 중단하고 다시 로그인하도록 안내합니다. 기존 브라우저 저장 기록과 현재 계산 결과는 보존하되, 다른 계정의 DB 결과는 노출하지 않습니다.
- 로그인 버튼을 연속 클릭해도 중복 로그인 흐름을 만들지 않으며, 로그인/로그아웃 뒤 뒤로 가기·새로고침·다른 탭에서도 계정 상태와 데이터 접근이 일치해야 합니다.
- 생년월일·출생시간과 해석은 민감하게 느껴질 수 있는 개인 데이터입니다. 로그인 페이지에서 필요한 최소 정보만 표시하고, 공용 브라우저에는 브라우저 기록이 남는다는 기존 경고를 유지합니다.

## 범위 밖

- 이메일/비밀번호, 다른 소셜 계정, Google One Tap, Google API 접근
- 결제, 전문가 상담, 계정 삭제·데이터 내보내기(별도 정책/Spec 필요)
- 기존 `localStorage` 기록의 자동 이전·삭제, DB 테이블/정책/저장 UI 구현(004에서 정의)
- Google/Supabase 계정의 실제 로그인 승인과 서비스 배포

## 완료 조건과 확인 사례

1. 비로그인 상태에서 사주 계산·기본 성향·기존 브라우저 기록 열람이 가능하고 로그인 버튼이 보입니다. 자세한 해석을 누르면 로그인 안내가 보이며 Gemini 호출·새 결과 저장은 일어나지 않습니다.
2. Google 로그인 성공 후 앱으로 복귀해 로그인 상태가 보이며, 새로고침 후에도 유지됩니다.
3. 로그인 취소·콜백 오류·공급자 설정 오류에서 비밀값 노출 없이 재시도 안내가 보이고 기존 브라우저 기록은 손상되지 않습니다.
4. 로그아웃하면 현재 세션만 종료되고 계정 전용 결과는 즉시 숨겨집니다. 다른 기기 세션과 DB 기록은 삭제되지 않습니다.
5. 쿠키를 조작하거나 세션이 만료된 상태에서 `/api/interpret` 또는 계정 전용 API를 호출하면 권한이 거부됩니다. 다른 사용자 계정으로 로그인해도 앞선 계정의 DB 기록을 볼 수 없습니다(004의 RLS 검사와 함께 확인).
6. 로그인 후 기존 브라우저 기록은 자동 업로드·삭제되지 않고, 로그인 뒤 새로 만든 해석 결과만 계정 DB에 저장됩니다(004와 함께 확인).
7. 관련 자동 테스트와 실제 브라우저에서 로그인·새로고침·로그아웃·실패·계정 전환 흐름을 확인합니다. 실제 Google 로그인은 사용자 본인의 Google 인증 협조가 필요할 수 있습니다.

## 구현·검증 현황 (2026-09-23)

- Supabase SSR 브라우저·서버 클라이언트, 세션 갱신 proxy, OAuth 콜백, Google 로그인·로그아웃 화면을 구현했습니다. `/api/interpret`는 서버에서 인증을 확인하고 비로그인 요청을 Gemini 호출 전에 거절합니다.
- 자동 테스트와 타입 검사, 배포용 빌드가 통과했습니다. 실제 브라우저에서는 비로그인 계산·로그인 안내·해석 차단과 이전 브라우저 기록 보존을 확인했습니다. Supabase Auth 설정 조회에서는 Google 공급자가 활성화되어 있었습니다.
- 실제 Google 계정 로그인·콜백·로그아웃과 다른 계정 전환은 아직 확인하지 못했습니다. 따라서 완료 상태로 표시하지 않습니다.
