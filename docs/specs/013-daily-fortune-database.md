# 013: 일일 운세 계정 DB 저장

## 목적과 사용자 정책

로그인 사용자의 오늘 운세를 계정에 보관해 같은 사주와 날짜의 문구를 다시 볼 수 있게 합니다. 사용자가 확정한 저장 단위는 **계정·출생 사주·한국 날짜별 한 건**이며, 오늘 운세가 표시될 때 자동 저장합니다. 출생 사주는 기존 지원 범위의 양력 생년월일과 출생시간 쌍으로 식별합니다. 같은 입력으로 자세한 해석 기록이 여러 건 있어도 오늘 운세는 한 건만 저장합니다.

## 사용자 흐름

1. 비로그인 사용자는 기존 012처럼 브라우저에서 계산한 오늘 운세를 봅니다. 계정 API 호출이나 DB 저장은 없습니다.
2. 로그인 사용자가 새 사주를 계산하거나 기존 계정·브라우저 기록을 열면, 오늘 운세를 즉시 표시하고 서버에 자동 저장을 요청합니다. 오래된 브라우저 기록을 계정에 자동 이전하는 것은 아닙니다. 로그인 상태에서 그 기록의 **오늘 운세 한 건만** 저장합니다.
3. 서버에 같은 계정·출생 정보·오늘 날짜의 운세가 이미 있으면 저장된 문구를 반환합니다. 문구 후보나 알고리즘이 이후 바뀌어도 저장된 그날의 문구를 우선 표시합니다. 새 날짜에는 새 운세를 계산해 저장합니다.
4. DB 저장이 확인되면 저장됨을 표시합니다. 저장에 실패하면 계산된 오늘 운세를 계속 보여주되 계정에 저장되지 않았음을 알리고 재시도 버튼을 제공합니다. 로그인 만료는 다시 로그인하도록 안내합니다. 전날 응답이 늦게 도착해도 새 날짜 화면을 덮어쓰지 않습니다.

## 데이터 모델과 접근 제어

새 테이블 `public.saju_daily_fortunes`를 재현 가능한 SQL migration으로 만듭니다.

| 열 | 형식·제약 | 의미 |
|---|---|---|
| `id` | UUID 기본값·기본키 | 운세 행 식별자 |
| `user_id` | UUID, `auth.users` 참조, `NOT NULL` | 검증된 로그인 소유자 |
| `birth_date`, `birth_time` | `date`, `time without time zone`, `NOT NULL` | 지원 범위에서 검증된 양력 출생 정보 |
| `fortune_date` | `date NOT NULL` | 한국 날짜 |
| `today_pillar` | 길이 2의 간지 `text NOT NULL` | 그 날짜 정오의 일주 |
| `flow`, `action`, `caution` | 비어 있지 않은 `text NOT NULL` | 화면에 보여준 세 문구의 스냅샷 |
| `fortune_version` | 양의 정수 | 문구 규칙 버전 |
| `created_at` | `timestamptz NOT NULL DEFAULT now()` | 최초 저장 시각 |

- `(user_id, birth_date, birth_time, fortune_date)`에 고유 제약을 둬 중복 요청·동시 요청에도 한 건만 남깁니다. 사용자·날짜 조회 인덱스는 고유 제약 인덱스를 활용합니다.
- RLS를 켜고 `authenticated`에 본인 행의 `SELECT`, `INSERT`만 허용합니다. `anon`에는 권한을 주지 않습니다. `UPDATE`와 `DELETE`는 이번 기능에서 제공하지 않습니다. 행의 `user_id`는 요청 본문이 아닌 서버의 검증된 세션에서 결정합니다.
- 원래 생년월일과 출생시간은 계정 DB에 저장됩니다. 이는 기존 해석 기록과 같은 범위의 개인정보입니다. Gemini나 새로운 외부 서비스에는 보내지 않습니다.

## API와 신뢰 경계

- `POST /api/daily-fortune`은 `{date, time}`만 받습니다. 과도한 본문, 잘못된 입력, 비로그인·만료 세션을 거부합니다. 응답은 `Cache-Control: no-store`입니다.
- 서버는 `lib/saju`로 출생 사주를 재계산하고, 서버의 현재 시각으로 한국 날짜를 정합니다. 클라이언트가 보내는 `user_id`, `chart`, `fortune_date`, 문구는 신뢰하거나 저장하지 않습니다.
- 먼저 검증된 사용자 범위에서 해당 행을 조회합니다. 기존 행은 저장값의 날짜·일주·문구 형식을 검사한 뒤 반환합니다. 새 행은 서버 계산값을 삽입하고 저장 확인된 행을 반환합니다. 고유 제약 충돌 시 기존 행을 다시 읽어 반환합니다.
- 기존 행이 손상됐거나 조회·삽입에 실패하면 저장 성공처럼 응답하지 않습니다. 인증 실패는 로그인 안내, 일시적인 DB 실패는 재시도 가능한 오류로 구분합니다. 로그에 출생 정보나 운세 원문을 남기지 않습니다.

## 범위에서 제외

- 과거 날짜 운세 목록·삭제·수정, 브라우저 기록 전체의 계정 이전, 알림
- Gemini 일일 운세 생성과 기존 자세한 해석 DB 구조 변경
- 비로그인 운세의 저장 또는 다른 사람의 운세 공유

## 완료 조건

1. 로그인한 같은 계정·사주·한국 날짜의 반복 조회와 동시 요청은 한 행만 저장하고 저장 문구를 반환합니다. 다른 사주·날짜·계정은 별도 행으로 저장됩니다.
2. 비로그인과 조작된 사용자 ID·사주 결과·운세 문구는 계정 DB 쓰기를 유발하지 않습니다. RLS에서 타인 행의 조회·삽입을 거부합니다.
3. 새 계산, 계정 기록 재열기, 브라우저 기록 재열기, 새로고침, 한국 자정 갱신에서 오늘의 저장 운세와 저장 상태가 일치합니다. 오래된 응답은 다른 사주나 날짜의 화면을 덮지 않습니다.
4. DB 실패·로그인 만료·손상된 저장 행에는 저장 성공 표시가 없고 재시도·로그인 안내가 나타납니다. 비로그인 운세와 기존 자세한 해석 기능은 계속 동작합니다.
5. 관련 자동 테스트, 타입 검사, 빌드, 가능한 실제 화면 및 DB 검증을 수행합니다. DB migration이 실제 대상 환경에 적용되지 않았다면 상태를 완료로 표시하지 않습니다.

## 검증 결과

- 2026-09-28: `saju_daily_fortunes` migration과 `POST /api/daily-fortune`을 작성했습니다. 서버가 출생 사주·한국 오늘 날짜를 다시 계산하고, 기존 행을 우선 읽거나 새 행을 저장합니다. 화면에는 저장 중·저장됨·미저장/재시도·로그인 만료 상태를 구분해 표시합니다.
- 비구현 테스트 담당이 인증, 기존 행 재사용, 조작 필드 무시, 계정·출생 사주별 분리, 동시 삽입 충돌, 손상 행과 DB 오류, RLS migration, 화면 연결을 검사했습니다. 주 에이전트의 `npm run check`에서 타입 검사와 전체 테스트 94개가 통과했고 `npm run build`도 통과했습니다.
- 로컬 브라우저에서 비로그인 상태로 이전 브라우저 기록을 열어 오늘 운세가 계속 표시되고 계정 저장 상태가 표시되지 않는 것을 확인했습니다.
- 제공받은 `sta-saju` Supabase 프로젝트(`dsqxrsqynqbspfkxbnaw`)의 SQL Editor에서 같은 이름의 테이블이 없는 것을 확인한 뒤 migration을 실행했고 `Success. No rows returned`를 확인했습니다. 다시 조회해 테이블 존재, RLS 활성화, 본인 행 조회·삽입 정책 2개, 계정·출생 정보·날짜의 고유 제약 1개를 확인했습니다. `anon`의 `SELECT`와 `authenticated`의 `UPDATE`·`DELETE` 권한은 없고, `authenticated`의 `SELECT`·`INSERT` 권한만 있습니다.
- Supabase 프로젝트의 공개 연결 설정을 로컬 실행 프로세스에만 주입하고 사용자 Google 로그인 후 기존 브라우저 기록 `2000-01-01 12:00`을 열었습니다. 화면에서 `계정에 저장됐어요.`를 확인했고, 새로고침 후 같은 기록을 다시 열어도 저장 상태와 문구가 유지됐습니다. SQL Editor에서 해당 사주·날짜의 행이 **1건**이고 저장된 `flow`가 화면 문구와 일치함을 확인했습니다. 기존 브라우저 기록 자체는 계정 해석 목록으로 이전되지 않았습니다.
- 로컬 검증용 공개 키는 코드와 Git에 저장하지 않았습니다. 현재 코드의 배포 후 실제 URL 동작은 이번 검증에 포함하지 않았습니다.
